# 模块 2：LLM 调用与输出控制

## 模块目标

能组织多轮对话上下文，合理选择模型参数，并实现可靠的文本与结构化输出调用。

## 核心笔记

### 一次模型请求包含什么

- **一句话结论：** 请求通常由模型选择、指令/上下文、用户输入和生成约束组成；具体字段名依 API 和模型而异。
- **提示：** 别把某一家 API 的参数名当作所有模型服务的通用标准。

### 消息角色与对话历史

- **developer / system：** 应用设定的行为规则和任务约束；具体角色和优先级依 API 而异。
- **user：** 当前用户输入或提供的数据。
- **assistant：** 模型生成的回复；要让模型利用历史对话，应用需传入历史消息，或使用该 API 支持的对话状态机制。
- **易错点：** role 是有约定的固定值，例如 assistant，不是随意写 ai。

### 多轮对话状态

- **一句话结论：** 模型不会因为上一轮请求发生过就自动记住内容；应用必须再次传入相关历史，或使用服务提供的对话状态功能。
- **无状态调用：** 每次请求携带本轮需要的指令、历史和新输入；省略历史时，代词或“刚才那个”可能失去上下文。
- **持久化与上下文不同：** 数据库可保存完整会话；实际发给模型的上下文应筛选相关历史并遵守 token 预算。
- **常用控制：** 保留固定应用指令和近期对话；必要时摘要较早内容或检索相关历史，避免无限追加整段聊天。
- **关联：** 当前会话上下文管理 → RAG 检索外部知识 → Agent Memory 选择长期保留的信息。

### Temperature 与输出长度上限

- **Temperature：** 调节采样的随机程度，不代表模型质量或聪明程度；低值通常更稳定，但不能保证每次输出完全相同。
- **输出 token 上限：** 限制生成的最大 token 数，不是要求模型一定生成这么多；过小可能使回答或结构化内容不完整。
- **易错点：** 参数名称、支持范围、是否支持 temperature 都可能依服务商和模型而不同；查目标模型的官方文档。

### 上下文窗口

- **一句话结论：** 输入历史和生成内容都消耗上下文预算；消息越长，可用于本轮输出的空间越少。
- **关联：** 对话历史管理 → Token 预算 → 后续的 RAG 上下文选择与压缩。
